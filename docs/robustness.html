ATLAS Threshold Detection Rules Analysis: all metrics with uncertainty, and how far the recommendations can be trusted

Summary

The tables below bring the three rules together. Comparing a miss rate with a false-positive rate across rules says little about priority by itself, because the two errors cost different amounts. Under the stated cost ratios, expected cost over the review window (in units of one false alarm) is 1,145 for Lateral Movement, 590 for Data Exfiltration and 300 for Brute Force Login. On that basis Lateral Movement is the first priority. The ranking depends on the cost ratios, which are illustrative.

Display code 
ci_text <- function(x, lo, hi) str_glue("{pct(x)} ({pct(lo)}–{pct(hi)})")

results |>
  transmute(
    rule,
    frr = ci_text(frr, frr_lo, frr_hi),
    far = ci_text(far, far_lo, far_hi),
    precision = pct(precision),
    prevalence = pct(prevalence),
    d_prime = number(d_prime, 0.01),
    mean_frr_far = pct(mean_frr_far),
    eer = pct(eer)
  ) |>
  kable_house(
    col.names = c("Detection rule", "FRR (95% CI)", "FAR (95% CI)", "Precision", "Prevalence",
                  "d′", "Mean of FRR & FAR", "Model EER")
  )

How to read the table. Each row is one rule. The miss rate (FRR) and false-alarm rate (FAR) show a 95% range in brackets, the span the true rate plausibly lies in given the sample size. Precision is the share of alerts that are real; prevalence is the share of events that are threats. d′ scores how well the rule tells threats from normal activity; higher is better. The last two columns compare a quick shortcut with the modelled equal error rate.

What the table tells you. The ranges are wide. Lateral Movement’s true miss rate could lie anywhere from 35.6% to 54.8%, because each rule saw only 100 real threats. Brute Force Login has the lowest d′ (1.61), so no setting can lower both of its errors at once. The shortcut overstates Lateral Movement’s equal error rate (23.6% against 14.3%); the two agree only at the crossing point, as for Data Exfiltration.

    eer_conf = pct(eer_conf, 1),

                  "Confidence", "Cost ratio", "Cost-weighted rationale"),
    escape = FALSE

How to read the table. Each row is one rule. The first pair of columns gives the action under the equal-error method and the share of 10,000 resampled datasets that reproduce it. The second pair does the same for the cost-weighted method. The cost ratio is how many false alarms one missed threat is judged to be worth, and the rationale explains the cost-weighted action. Actions reproduced less than 80% of the time are marked low confidence.

What the table tells you. The two methods agree, with stable answers, only for Lateral Movement. They diverge elsewhere because the equal-error method quietly values a miss at 9 false alarms for every rule, while the cost-weighted method uses each rule’s stated ratio. Where the methods disagree, the deciding input is that cost ratio. Setting it is a risk-appetite decision for leadership, not a technical setting for engineers.

Recommendation robustness

Each rule’s counts were resampled 10,000 times from binomial distributions with the observed rates, and both decision rules were re-applied to every draw (see Methodology). The table shows the share of draws giving each action. A recommendation reproduced in fewer than 80% of draws is labelled low confidence.

Display code 
actions <- c("TIGHTEN", "HOLD", "LOOSEN", "IMPROVE SIGNAL")

boot |>
  mutate(action = factor(action, levels = actions)) |>
  complete(rule, method, action, fill = list(share = 0)) |>
  filter(!(method == "EER-based" & action == "IMPROVE SIGNAL")) |>
  mutate(
    share = pct(share, 0.1),
    rule = factor(rule, levels = results$rule),
    method = factor(method, levels = c("EER-based", "Cost-weighted"))
  ) |>
  pivot_wider(names_from = action, values_from = share, values_fill = "–") |>
  arrange(rule, method) |>
  kable_house(col.names = c("Detection rule", "Decision rule", actions))

How to read the table. Each rule has two rows, one per decision method. Each cell is the share of 10,000 simulated re-runs that produced that action. Every re-run draws new counts from the same rates, adding the random variation a fresh review window would bring. A dash means the method cannot produce that action. A share near 100% means the recommendation is stable; shares spread across several actions mean the data cannot settle the question.

What the table tells you. Only Lateral Movement gets a stable answer from both methods. Brute Force Login’s equal-error TIGHTEN rests on a 2.2-point gap against a 2-point tolerance, so chance alone often flips it. Data Exfiltration’s equal-error HOLD is close to a coin toss: a rule sitting exactly on the crossing point lands outside the tolerance about half the time. Its cost-weighted LOOSEN is stable.

Sensitivity to threat prevalence

Precision depends on how rare threats are. The table holds each rule’s FRR and FAR fixed and recomputes precision at lower prevalence.

Display code 
prevalence_tbl |>
  mutate(precision = pct(precision), p = str_glue("Prevalence {percent(p, accuracy = 0.1)}")) |>
  select(rule, p, precision) |>
  pivot_wider(names_from = p, values_from = precision) |>
  kable_house(col.names = c("Detection rule", str_glue("Prevalence {percent(params$prevalence_grid, accuracy = 0.1)}")))

How to read the table. Each row is one rule, with its current miss and false-alarm rates held fixed. Each column assumes a different share of events that are real threats: 10% (this dataset), then 1% and 0.1%. Each cell is the resulting precision, the share of the rule’s alerts that would be real threats. Reading across a row shows how quickly the alert queue fills with false alarms as real threats become rarer.

What the table tells you. This dataset’s 10% prevalence makes the queues look far healthier than in a real SOC, where threats are usually well under 1% of events. At 0.1%, at most 2.4% of alerts from any rule would be real, so false-alarm rates of 22.2% or 10.0% would bury analysts. The cost-weighted settings, which raise false alarms, need real prevalence and volume data before anyone acts on them.

Interpretation notes

TIGHTEN rules generate alert volumes out of proportion to the threat rate. Raising the threshold cuts tickets immediately, but monitor FRR afterwards. Tightening’s downside is hard to observe: new misses stay invisible until the next labelled window. Stage the change where possible. Move the threshold partway, hold for one review period, and confirm FRR is still acceptable before tightening further.

LOOSEN rules have the opposite problem: threats are slipping through. A lower threshold catches more, but increases analyst workload, by the amounts shown in the projection table. Pair loosening with suppression or case-grouping logic where possible. Loosening without more triage capacity only moves the fatigue problem from one rule to another, and most of the extra alerts will still be benign. Budget for the added volume before implementing the change, not after.

HOLD rules sit near their target threshold. Routine monitoring is enough; flag the rule for review if attacker behaviour or data volume shifts materially. A rule can drift out of HOLD without any change to its own threshold. A new attacker technique, a new benign traffic pattern from an infrastructure change, or a change in overall event volume can each move a rule’s real FRR and FAR. HOLD therefore keeps the same review cadence as the other actions, without the same urgency.

IMPROVE SIGNAL rules separate threats from benign events too poorly for any threshold to help much. The next step is engineering work on the rule’s features, followed by a fresh labelled window to measure the new d′.

NoteATLAS cycle: next steps

After implementing threshold changes, re-run this analysis with the confusion-matrix values from the next review period. As a textbook illustration, the DataSecure Inc. example (Mattei 2025, §8.5.5) shows FRR falling from 3% to 0.5%, FAR from 1% to 0.2%, and EER from 2% to 0.35% across one improvement cycle. Those rates are an order of magnitude below the rules here, so the example shows the shape of an improvement cycle, not an expected trajectory for these rules. Such gains come from repeated Measure → Report → Select cycles rather than a single threshold move. Lateral Movement in particular is likely to need more than one cycle.

## Recommendation robustness {#sec-robustness}

Each rule's counts were resampled `r comma(params$bootstrap_draws)` times from binomial distributions with the observed rates, and both decision rules were re-applied to every draw (see [Methodology](methodology.qmd#uncertainty)). The table shows the share of draws giving each action. A recommendation reproduced in fewer than `r pct(params$confidence_threshold, 1)` of draws is labelled low confidence.

```{r}
#| label: tbl-bootstrap
#| tbl-cap: "Share of resamples giving each action, by rule and decision rule"
actions <- c("TIGHTEN", "HOLD", "LOOSEN", "IMPROVE SIGNAL")

boot |>
  mutate(action = factor(action, levels = actions)) |>
  complete(rule, method, action, fill = list(share = 0)) |>
  filter(!(method == "EER-based" & action == "IMPROVE SIGNAL")) |>

    share = pct(share, 0.1),
    rule = factor(rule, levels = results$rule),
    method = factor(method, levels = c("EER-based", "Cost-weighted"))

  pivot_wider(names_from = action, values_from = share, values_fill = "–") |>
  arrange(rule, method) |>

```

**How to read the table.** Each rule has two rows, one per decision method. Each cell is the share of `r comma(params$bootstrap_draws)` simulated re-runs that produced that action. Every re-run draws new counts from the same rates, adding the random variation a fresh review window would bring. A dash means the method cannot produce that action. A share near 100% means the recommendation is stable; shares spread across several actions mean the data cannot settle the question.

**What the table tells you.** Only `r paste(robust_rules$rule, collapse = " and ")` gets a stable answer from both methods. Brute Force Login's equal-error `r bf$eer_action` rests on a `r number(abs(bf$far - bf$frr) * 100, 0.1)`-point gap against a `r number(params$eer_tolerance * 100, 1)`-point tolerance, so chance alone often flips it. Its cost-weighted `r exf$cost_action` is stable.
