ATLAS Threshold Detection Rules Analysis: inputs, calibration charts and projected workload by rule

This page sets out the input data, then takes each rule in turn: its calibration chart, both recommendations, and what the numbers mean operationally. It ends with the projected change in detections and analyst workload if each rule moves to its EER or its cost-optimal threshold. Definitions are on Methodology. The limits of this analysis are listed under Known limitations.

Detection rules

WarningIllustrative data

The counts are constructed for teaching and do not come from a production SOC. Each rule uses 1,000 events and 100 threats (10% prevalence). The units, windows, sources of missed-threat labels and cost ratios are illustrative too.

Each row is one rule’s classification outcomes over a fixed, labelled review window. True positives and false negatives make up the threat population that FRR is measured against. False positives and true negatives make up the benign population that FAR is measured against. The unit defines what one event is, and so sets the denominator of FAR. The FN source says how missed threats were found, which matters because each source has its own blind spots. The cost ratio is the cost of one missed threat expressed in false alarms; it is a risk-appetite input, not a measurement. To analyse a different rule set, edit rules in params.yaml and re-render.

Display code 
rules |>
  select(rule_name, unit, window_days, fn_source, tp, fp, fn, tn, cost_ratio) |>
  mutate(cost_ratio = str_glue("{cost_ratio}:1")) |>
  kable_house(
    col.names = c("Detection rule", "Unit of analysis", "Window (days)", "FN source",
                  "TP", "FP", "FN", "TN", "Cost ratio (miss : false alarm)")
  )

How to read the table. Each row is one detection rule over a 30-day review. The unit column says what counts as one event, and the FN source says how missed threats were discovered. TP counts real threats caught, FP harmless events flagged, FN real threats missed, and TN harmless events correctly ignored. The final column states how many false alarms one missed threat is judged to be worth, which is a risk-appetite setting.

What the table tells you. Every rule saw 1,000 events, 100 of them real threats, so differences between rules come from their settings and detection logic, not from data volume. Brute Force Login raises the most false alarms (200) and Lateral Movement misses the most threats (45). Data Exfiltration carries the highest cost ratio, 50:1, because a missed data theft is the most damaging outcome here. These counts are illustrative.

Brute Force Login

Display code 
plot_rule(bf)

How to read the plot. The horizontal axis is the rule’s alert threshold in model units; moving right means fewer alerts. The red curve is the share of harmless events flagged and the blue curve the share of real threats missed. The dotted line marks today’s setting and the dashed line the lowest-cost setting. The open circle is where the two error rates are equal: the equal error rate (EER).

What the plot tells you. Today’s setting sits almost on the crossing point: 20.0% of attacks are missed and 22.2% of harmless events are flagged. The curves cross at a high level (EER 21.1%), which shows the rule separates attacks from normal activity poorly. Moving to the lowest-cost setting would cut false alarms but miss more attacks, saving only 8.5% of expected cost. The fix is better detection logic, not a new setting.

Cost-weighted: IMPROVE SIGNAL (reproduced in 68% of resamples, low confidence). Separability is low (d′ = 1.61) and moving to the cost-optimal threshold (FRR 33.1%, FAR 12.1%) cuts expected cost by only 8.5%. Better detection features are needed before a threshold change pays off.

EER-based: TIGHTEN (reproduced in 53% of resamples, low confidence). FAR (22.2%) exceeds FRR (20.0%) by 2.2 percentage points: raise the threshold towards the EER.

Brute Force Login is already close to its EER. Under the model, the current threshold sits 0.04 model units below the EER threshold. Moving there would cut false positives from 200 to about 190, roughly 5%. The rule flags about 2.5 benign events for every real attempt it catches (200 false positives against 80 true positives). That ratio reflects low precision at this prevalence, not a FAR–FRR imbalance, and a threshold tweak will not fix it.

The rule’s real problem is weak separability: d′ = 1.61. Even the cost-optimal threshold only trades 13 fewer detections for 91 fewer false alarms. Raising a per-account failed-attempt count would also make the rule easier to evade with password spraying and low-and-slow credential stuffing, which stay under per-account thresholds by design. Better levers improve the signal: count distinct accounts per source, group by source IP or ASN, alert on a success that follows failures, and allowlist known service accounts and single-sign-on retry patterns.

Lateral Movement

Display code 
plot_rule(lat)

How to read the plot. The horizontal axis is the rule’s alert threshold in model units; moving right means fewer alerts. The red curve is the share of harmless events flagged and the blue curve the share of real threats missed. The dotted line marks today’s setting and the dashed line the lowest-cost setting. The open circle is where the two error rates are equal: the equal error rate (EER).

What the plot tells you. Today’s setting sits far to the right of the crossing point. The rule flags only 2.2% of harmless events but misses 45.0% of real attacks. The lowest-cost setting lies well to the left, where it would miss 6.1% of attacks and flag 27.8% of harmless events. That move would cut expected cost by 64.8%, but it would sharply increase the number of alerts analysts must handle.

Cost-weighted: LOOSEN (reproduced in 100% of resamples). Lower the threshold to the cost-optimal point (FRR 6.1%, FAR 27.8%); expected cost falls by 64.8%.

EER-based: LOOSEN (reproduced in 100% of resamples). FRR (45.0%) exceeds FAR (2.2%) by 42.8 percentage points: lower the threshold towards the EER.

Lateral Movement misses 45.0% of confirmed lateral-movement events (95% CI 35.6%–54.8%), while its FAR is only 2.2%. It is the only rule whose recommendation holds up under resampling with both decision rules. One hypothesis, not tested here, is that the rule was tuned conservatively to avoid flagging legitimate administrative activity such as RDP or PsExec use by IT staff. Lateral movement is often the step between an initial foothold and the attacker’s objective, so a rule that catches only about half of it leaves a wide window for an intrusion to progress.

Loosening has a measurable cost. Moving to the EER would add about 31 detections and 109 false alarms per window, and precision would fall from 73.3% to 40.0%. At 15 minutes per alert, that is about 27 extra analyst hours per window. Moving all the way to the cost-optimal threshold adds 39 detections and 230 false alarms (58 hours). At realistic prevalence the added false alarms would be far larger. Behavioural detections may close the gap more cheaply than one numeric threshold: first-seen host pairs, remote service creation, writes to admin shares, and PsExec or WMI launched from non-admin sources, combined with allowlisting jump hosts and admin tooling.

Data Exfiltration

plot_rule(exf)

How to read the plot. The horizontal axis is the rule’s alert threshold in model units; moving right means fewer alerts. The red curve is the share of harmless events flagged and the blue curve the share of real threats missed. The dotted line marks today’s setting and the dashed line the lowest-cost setting. The open circle is where the two error rates are equal: the equal error rate (EER).

What the plot tells you. Today’s setting sits exactly on the crossing point, missing 10.0% of attacks and flagging 10.0% of harmless events. That balance treats one missed data theft as costing only 9 false alarms. At the stated 50:1, the lowest-cost setting lies to the left: misses fall to 2.6%, but false alarms rise to 27.0%. Its crossing point is the lowest of the three rules, so it separates threats from normal activity best.

Cost-weighted: LOOSEN (reproduced in 100% of resamples). Lower the threshold to the cost-optimal point (FRR 2.6%, FAR 27.0%); expected cost falls by 37.1%.

EER-based: HOLD (reproduced in 47% of resamples, low confidence). FRR (10.0%) and FAR (10.0%) are within 2 percentage points of each other.

Data Exfiltration sits at its EER: FRR is 10.0% and FAR is 10.0%. The EER-based HOLD is fragile, though: it is reproduced in only 47% of resamples. Given this rule’s consequence (confirmed data loss), the cost-weighted analysis favours a lower FRR than the EER. HOLD at the EER implicitly assumes a 9:1 miss-to-false-alarm cost ratio; at the stated 50:1, the cost-optimal threshold cuts FRR to 2.6% but raises FAR to 27.0%. That would add about 153 false alarms per window (38 analyst hours). Moving the threshold only trades one error for the other. Lowering both requires a materially better detection signal, such as destination reputation, user and host baselines, or data-classification context.

Projected change at the recommended threshold

The table shows what the model predicts for each rule at two targets, the EER and the cost-optimal threshold, over the same review window. Changes are relative to the current counts. Extra analyst hours assume 15 minutes to triage each alert.

How to read the table. Each rule appears twice: once moved to its equal-error setting and once to its lowest-cost setting. Arrows show today’s count and the predicted count over a 30-day window, and the change columns give the difference. Precision is the share of alerts that are real threats. The last column converts the change in false alarms into analyst time at 15 minutes per alert; negative numbers mean time saved.

What the table tells you. Making Lateral Movement more sensitive buys detections at a steep price. At its equal-error setting it catches about 31 more threats but adds about 109 false alarms, roughly 27 extra analyst hours per window. Brute Force Login’s lowest-cost setting saves about 23 hours but misses 13 more attacks. These predictions come from a model anchored to one data point, so treat them as rough sizes, not forecasts.

```{r load}
bf  <- res[["Brute Force Login"]]

conf_note <- function(conf) {
  low <- if (conf < params$confidence_threshold) ", low confidence" else ""
  str_glue("reproduced in {pct(conf, 1)} of resamples{low}")
}

rec_line <- function(r) {
  str_glue(
    "**Cost-weighted: {r$cost_action}** ({conf_note(r$cost_conf)}). {r$cost_reason}\n\n",
    "**EER-based: {r$eer_action}** ({conf_note(r$eer_conf)}). {r$eer_reason}"
  )
}
```

`r rec_line(bf)`

Brute Force Login is already close to its EER. Under the model, the current threshold sits `r number(abs(bf$t_eer - bf$t_current), 0.01)` model units `r if_else(bf$t_current < bf$t_eer, "below", "above")` the EER threshold.
