Reproducibility

ATLAS Threshold Detection Rules Analysis: how to rerun the analysis and where the results can mislead

Every number on this site is computed from the illustrative confusion-matrix counts and assumptions in params.yaml. Nothing is downloaded during a render, and the only random step (the resampling check) uses a fixed seed, so rendering the same commit with the same package versions gives the same results. This page explains how to rebuild the site, records the environment it was built in, and states where the results can mislead. It is re-executed on every render, so the tests and environment status below are always current.

Quick start

The code is in the GitHub repository patrick-lefler/atlas-detection-rules-analysis. To rebuild everything from a clean copy:

git clone https://github.com/patrick-lefler/atlas-detection-rules-analysis
cd atlas-detection-rules-analysis
Rscript -e 'renv::restore()'   # once: install the package versions pinned in renv.lock
quarto render

The rendered site is written to docs/.

Parameters and seeds

All inputs live in params.yaml: the confusion-matrix counts and descriptions of each rule, the cost ratios, the decision-rule settings, the resampling settings, the prevalence grid and analyst minutes per alert. Each value is labelled as illustrative, an assumption or a reporting convention, and assumptions carry a plausible range. The only random step is the resampling check in bootstrap_rule(), which calls set.seed(2026) at the start of each rule, so a rule’s result does not depend on the order of the rules or on the number of cores.

Noteparams.yaml 
# Every input that drives the analysis. Each value is labelled:
#   [illustrative] constructed for teaching; not from a production SOC
#   [assumption]   a modelling or policy choice; change it to match your risk appetite
#   [convention]   a reporting choice with no effect on the underlying numbers

# Detection rules [illustrative]. Confusion-matrix counts at the current threshold
# over one labelled review window. Each rule has 1,000 events and 100 threats (10% prevalence).
#   unit:        what counts as one event (sets the denominator of the false-positive rate)
#   window_days: length of the labelled review window
#   fn_source:   how missed threats (false negatives) were identified
#   cost_ratio:  cost of one missed threat / cost of one false alarm [assumption],
#                illustrative; set from risk appetite. Plausible range 1-1000.
rules:
  - rule_name: "Brute Force Login"
    tp: 80
    fp: 200
    fn: 20
    tn: 700
    unit: "account-hour with failed logins"
    window_days: 30
    fn_source: "purple-team replay"
    cost_ratio: 5
  - rule_name: "Lateral Movement"
    tp: 55
    fp: 20
    fn: 45
    tn: 880
    unit: "host-pair admin session"
    window_days: 30
    fn_source: "purple-team replay"
    cost_ratio: 25
  - rule_name: "Data Exfiltration"
    tp: 90
    fp: 90
    fn: 10
    tn: 810
    unit: "outbound flow-hour per host"
    window_days: 30
    fn_source: "retro-hunt and DLP incidents"
    cost_ratio: 50

# EER-based rule (the original ATLAS reading) [assumption]
# HOLD when |FRR - FAR| is within this many proportion units (0.02 = 2 percentage points). Range 0.01-0.05.
eer_tolerance: 0.02

# Cost-weighted rule [assumption]
# HOLD when the current threshold is within this distance (model z-units) of the cost-optimal one. Range 0.05-0.25.
delta_t: 0.1
# IMPROVE SIGNAL when separability d' is below this AND moving to the cost-optimal threshold
# cuts expected cost by less than min_cost_reduction.
improve_signal_d_prime: 2
improve_signal_min_cost_reduction: 0.10

# Robustness [convention]
bootstrap_draws: 10000
seed: 2026
# A recommendation reproduced in fewer than this share of resamples is flagged "low confidence".
confidence_threshold: 0.80
ci_level: 0.95

# Prevalence sensitivity [assumption]: threat share of events to test precision against.
prevalence_grid: [0.10, 0.01, 0.001]

# Workload [assumption]: analyst minutes to triage one alert. Range 5-60.
analyst_minutes_per_alert: 15

Tests

Core functions are covered by testthat tests in tests/testthat/. They check the error-rate formulas and published Wilson intervals, that the model passes through the observed point and finds the crossover, that the cost-optimal threshold matches a numerical minimum and reduces to the EER at a cost ratio of (1 − p)/p, both decision rules, determinism of the bootstrap, the workload projection and the empirical curve. Known limitations

Limits of reproducibility

  • Bit-for-bit equality is expected only on the same platform and package versions. Floating-point and BLAS differences across machines can change low-order digits.
  • The resampling check depends on R’s default random number generator. A future change to rbinom() or the default generator could shift the resampled shares slightly.
  • Quarto versions affect rendering, not the numbers.

Model limitations

  1. The data are illustrative. Each rule has 1,000 events and 100 threats. The results show the method, not the performance of any real rule.
  2. Missed-threat labels carry verification bias. False negatives can only be counted where something else found the threat: red- or purple-team exercises, retro-hunts, or incidents caught by other controls. Each source finds some kinds of attack more easily than others, so FRR is the least reliable number here, and it drives the most consequential recommendation.
  3. FAR depends on the unit of analysis. What counts as one benign event (an authentication, a session, a flow-hour) sets the FAR denominator. A different unit can move FAR by an order of magnitude without any change to the rule.
  4. The curves are assumed, not fitted. The equal-variance Gaussian model is anchored to a single observed point, so it passes through that point by construction. Real scores are often skewed, heavy-tailed or discrete. See empirical curves for the alternative.
  5. Thresholds are in model units. The charts’ x-axis is a benign-score z, not a SIEM configuration value. Putting a recommendation into practice means mapping it to real units.
  6. Rules are evaluated in isolation. Defence in depth is ignored: a threat one rule misses may be caught by another control. Detection latency is ignored too, though for lateral movement a late detection can be nearly as bad as a miss.
  7. Samples are small. With about 100 threats per rule, the intervals are wide and two of the three EER-based recommendations are not robust; see Recommendation robustness.
  8. Prevalence is unrealistically high. At 10% prevalence the queues look far healthier than they would in production; see Sensitivity to threat prevalence.
  9. Cost ratios are illustrative. The cost-weighted recommendations depend directly on them.

What would change the conclusions

Assumption Current value Conclusion that would change
Data Exfiltration cost ratio 50:1 At 9:1 the cost-optimal and EER thresholds coincide and LOOSEN becomes HOLD.
Brute Force Login cost ratio and the IMPROVE SIGNAL cut-offs 5:1; d′ < 2, gain < 10% A lower cost ratio or a lower gain cut-off returns TIGHTEN instead of IMPROVE SIGNAL.
Lateral Movement missed-threat count 45 of 100 If purple-team replays overstate misses, FRR and the size of the LOOSEN move shrink.
Prevalence 10% At realistic prevalence, cost-weighted thresholds that raise FAR would produce unmanageable alert volumes.

What real data would replace each assumption

Assumption Replace with
Constructed counts Confusion matrices from a fixed, labelled review window per rule
One observed point per rule Counts at several real thresholds from replayed logs, fed to build_empirical_curve()
Unit of analysis and window The unit the rule actually scores and the dates of the review window
Missed-threat labels Documented purple-team, retro-hunt and incident sources, with coverage notes
Cost ratios A per-rule ratio agreed with risk owners, linked to the risk-appetite statement
Analyst minutes per alert Median triage time per rule from the case-management system

How to use these results. Use them to learn the method, to see how recommendations depend on stated costs and on sampling noise, and as a template for a real calibration record. Do not use them as evidence about any real rule’s performance, or to set a production threshold without measured counts, real threshold units and an agreed cost ratio.

## Known limitations {#limitations}

### Limits of reproducibility {#repro-limits}

-   Bit-for-bit equality is expected only on the same platform and package versions. Floating-point and BLAS differences across machines can change low-order digits.
-   The resampling check depends on R's default random number generator. A future change to `rbinom()` or the default generator could shift the resampled shares slightly.
-   Quarto versions affect rendering, not the numbers.

### Model limitations {#sec-limitations}

1.  **The data are illustrative.** Each rule has `r comma(res[[1]]$n_threat + res[[1]]$n_benign)` events and `r res[[1]]$n_threat` threats. The results show the method, not the performance of any real rule.
2.  **Missed-threat labels carry verification bias.** False negatives can only be counted where something else found the threat: red- or purple-team exercises, retro-hunts, or incidents caught by other controls. Each source finds some kinds of attack more easily than others, so FRR is the least reliable number here, and it drives the most consequential recommendation.
3.  **FAR depends on the unit of analysis.** What counts as one benign event (an authentication, a session, a flow-hour) sets the FAR denominator. A different unit can move FAR by an order of magnitude without any change to the rule.
4.  **The curves are assumed, not fitted.** The equal-variance Gaussian model is anchored to a single observed point, so it passes through that point by construction. Real scores are often skewed, heavy-tailed or discrete. See [empirical curves](methodology.qmd#sec-empirical) for the alternative.
5.  **Thresholds are in model units.** The charts' x-axis is a benign-score z, not a SIEM configuration value. Putting a recommendation into practice means mapping it to real units.
6.  **Rules are evaluated in isolation.** Defence in depth is ignored: a threat one rule misses may be caught by another control. Detection latency is ignored too, though for lateral movement a late detection can be nearly as bad as a miss.
7.  **Samples are small.** With about `r res[[1]]$n_threat` threats per rule, the intervals are wide and two of the three EER-based recommendations are not robust; see [Recommendation robustness](robustness.qmd#sec-robustness).
8.  **Prevalence is unrealistically high.** At `r pct(res[[1]]$prevalence, 1)` prevalence the queues look far healthier than they would in production; see [Sensitivity to threat prevalence](robustness.qmd#sec-prevalence).
9.  **Cost ratios are illustrative.** The cost-weighted recommendations depend directly on them.

| Assumption | Current value | Conclusion that would change |
|:------------------------|:------------------|:-------------------------------------------|
| Data Exfiltration cost ratio | `r res[["Data Exfiltration"]]$cost_ratio`:1 | At `r number(res[["Data Exfiltration"]]$eer_implied_cost_ratio, 1)`:1 the cost-optimal and EER thresholds coincide and LOOSEN becomes HOLD. |
| Brute Force Login cost ratio and the IMPROVE SIGNAL cut-offs | `r res[["Brute Force Login"]]$cost_ratio`:1; d′ < `r params$improve_signal_d_prime`, gain < `r pct(params$improve_signal_min_cost_reduction, 1)` | A lower cost ratio or a lower gain cut-off returns TIGHTEN instead of IMPROVE SIGNAL. |
| Lateral Movement missed-threat count | `r res[["Lateral Movement"]]$fn` of `r res[["Lateral Movement"]]$n_threat` | If purple-team replays overstate misses, FRR and the size of the LOOSEN move shrink. |
| Prevalence | `r pct(res[[1]]$prevalence, 1)` | At realistic prevalence, cost-weighted thresholds that raise FAR would produce unmanageable alert volumes. |

**What real data would replace each assumption**

| Assumption | Replace with |
|:-------------------------------|:-------------------------------------------------|
| Constructed counts | Confusion matrices from a fixed, labelled review window per rule |
| One observed point per rule | Counts at several real thresholds from replayed logs, fed to `build_empirical_curve()` |
| Unit of analysis and window | The unit the rule actually scores and the dates of the review window |
| Missed-threat labels | Documented purple-team, retro-hunt and incident sources, with coverage notes |
| Cost ratios | A per-rule ratio agreed with risk owners, linked to the risk-appetite statement |
| Analyst minutes per alert | Median triage time per rule from the case-management system |

**How to use these results.** Use them to learn the method, to see how recommendations depend on stated costs and on sampling noise, and as a template for a real calibration record. Do not use them as evidence about any real rule's performance, or to set a production threshold without measured counts, real threshold units and an agreed cost ratio.
